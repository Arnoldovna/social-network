# Build order

Matches PLAN.md Etappe 2: **Scaffold (incl. CI/CD) → Backend modules (parallel) → Frontend modules (parallel) →
CSS & Design → Tests/E2E**. Every phase (and each Phase 1 sub-phase) ends with the `quality-gate` skill
(`pnpm verify`, `/code-review high`, `/simplify`, `pnpm verify`, conventional commit on a feature branch, PR,
`gh pr checks --watch`, squash-merge), one branch and one PR per phase or sub-phase
(`project-scaffold/references/conventions.md` §3). CI cost rule (ADR-0018): the `e2e` job runs on the PR only, so
`gh pr checks --watch` must show it green; after the merge, CI on `main` runs without `e2e`, and the `release.yml`
run it triggers shows `images` and `deploy` as skipped while the repository is private.

`project-scaffold/references/conventions.md` is binding for everything the three projects share (repo bootstrap,
branches, parallel model, script names, e2e and integration-test isolation, cookie names, digest pins,
CI/audit/release workflows). This file only adds social-network specifics. Where conventions are stale against
PLAN.md, PLAN.md wins and the ADR says so: Phase 0 tools (§1, ADR-0019 §1) and the CI cost rule (§9, ADR-0018).

Every agent:

- **Starts every shell command with `source ~/.devenv.sh && `** (Phase 0). The working directory
  is reset between calls, so use absolute paths (repo: `~/social-network`, plan:
  `~/PLAN.md`).
- Treats OVERVIEW.md, DATA-MODEL.md, API.md and the ADRs as binding. A needed change is made in the docs first and
  flagged, never silently in code.
- Writes English only. Nothing from the legacy code is copied (code, SQL, copy text, assets, values); no secret from
  the old Mac ever enters the repository.
- Fixes causes: never weakens, skips or deletes a test, never adds an `eslint-disable` without a same-line reason,
  never uses `@ts-ignore`.

Parallel rules (apply to phases 2–5):

1. A unit owns **only** the files listed for it. Everything else is read-only for that unit.
2. Composition files (`apps/api/src/app.ts`, `container.ts`, `server.ts`, `apps/web/src/main.tsx`,
   `apps/web/src/app/router.tsx`, layouts, header) and every feature's `index.ts` **signature** are created in
   Phase 1. Units fill in the body of their own `index.ts` but must not change its exported names or
   parameter/prop types.
3. Frozen after Phase 1: every file created in Phase 1 except the stubs a later unit's file list names explicitly
   (feature `index.ts` bodies, stub components, `db/seed/{cli,index}.ts`). In particular: `packages/shared`,
   `apps/api/src/shared`, `apps/api/src/config`, `apps/api/src/db/{client,migrate,selections}.ts`,
   `apps/api/src/db/schema`, `apps/api/drizzle`, `apps/api/src/{app,container,server}.ts`,
   `apps/api/src/features/friends/{friendship-state,friendship-reader}.ts` (+ their tests, ADR-0019 §3),
   **`apps/api/test/*`**, `apps/web/src/shared` (incl. `shared/test`), `apps/web/src/app/*.ts(x)` and
   `app/**/*.tsx` (not the `.css` files), `apps/web/src/main.tsx`, `apps/web/src/styles/tokens.css` and
   `styles/main.css`, `e2e/{a11y.ts,fixtures/*}`, all scripts, workflows, compose files and Dockerfiles.
   `styles/{base,utilities}.css`, `shared/ui/*.css` and `app/**/*.css` are frozen after Phase 4a (the only phase
   allowed to change them). A unit that needs a change to a frozen file stops and reports it; the orchestrator
   applies it serially between batches.
4. No new migration and no new dependency inside a parallel phase (migrations and the lockfile are sequential,
   orchestrator only). Units do not commit; the orchestrator runs one quality gate per phase.
5. Each unit ships its unit/integration/component tests with the code (house rule); E2E specs come in Phase 5.
   Test doubles and fixtures a unit needs beyond the generic Phase 1 helpers live in its own
   `__tests__/{fakes,fixtures}.ts`.
6. **Shared local resources.** Parallel units never run `pnpm dev`, `pnpm dev:setup`, `pnpm infra:*`,
   `pnpm stack:*`, `pnpm demo`, `pnpm test:e2e`, `pnpm e2e:*`, any docker compose command or the full
   `pnpm verify`: the dev project `social-network` uses fixed ports 3000, 5173, 5432, 6379, 9000, 9001 and 8080, and the
   e2e project `social-network-e2e` is owned by the orchestrator. Units verify with scoped commands only (conventions
   §4): `pnpm exec eslint <own paths>`, `pnpm --filter <pkg> typecheck` (fix only own errors),
   `pnpm exec vitest run --project <unit:… | integration:api> <own paths>` (Testcontainers starts its own containers
   on random ports and every test file gets its own database, so this is isolated). Units that write CSS (phases 3
   and 4) also run `pnpm exec stylelint "<own css glob>"` and `node scripts/check-no-utilities.mjs apps/web` (the
   checker needs all CSS to know which classes exist; fix only findings in own files, report the rest). The orchestrator runs the full
   `pnpm verify` once at the gate. Only the orchestrator starts or stops a stack (`pnpm demo` / `pnpm stack:down`
   around 4c, `pnpm e2e:up` / `pnpm e2e:down` around Phase 5).
7. **One working tree stays importable** (conventions §4, ADR-0019 §2). `createTestApp()` mounts every API module
   and `router.tsx` imports every web feature, so a sibling's half-written file can break everyone's scoped tests:
   - a unit writes its internal files first and replaces its stub `index.ts` **last**, after its internal files are
     complete and its own unit tests pass; the new `index.ts` keeps the frozen signature and never throws at import
     or at `create<Name>Module()` time;
   - every saved file parses (TS, TSX, CSS); write whole files, not partial drafts;
   - a test that renders another feature's public component mocks that feature's `index.ts` (`vi.mock`) with a
     trivial stand-in; the MSW server uses `onUnhandledFrame: 'error'`, so an unmocked sibling would fail the test
     as soon as the sibling swaps its `index.ts`;
   - API integration tests sign in through `test/http.ts#signIn(agent, userId)` (test-only route, ADR-0019 §3) with
     users from `test/db.ts#insertUser`; only the auth unit's own tests use the real `register()`/`login()`;
   - a failure caused by a sibling's file is reported to the orchestrator, never fixed by the unit.

## Phase 0 – Machine prerequisites and repository (done: `~/.devenv.sh`)

Phase 0 is **already satisfied** by `~/.devenv.sh` (PLAN.md Etappe 0, ADR-0019 §1). The script
changes nothing on the system, only the current shell:

- `PATH` starts with the newest installed nvm Node 26 (`~/.nvm/versions/node/v26.*`, 26.13.1 on 2026-11-17), then
  `/opt/homebrew/bin` (git 2.52, gh, docker CLI, gitleaks 8.30.1, lefthook). `pnpm` is a corepack shim that is
  already on the user's `PATH`; corepack runs exactly `package.json#packageManager` (`pnpm@10.34.9`), and
  `COREPACK_ENABLE_DOWNLOAD_PROMPT=0` keeps it non-interactive.
- Docker: when the Colima socket exists the script sets `DOCKER_HOST` to it, `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE`
  for Testcontainers and a shell-private `DOCKER_CONFIG` (`~/.docker/config.json` stays untouched); Compose 5.5
  (≥ 2.24.4 for `!reset`/`!override`). `gh` is logged in as Arnoldovna.
- Repository bootstrap (conventions §2) is done: `main` holds the docs-only commit, `origin` is the **private**
  `Arnoldovna/social-network`. Never change its visibility; Marina makes it public herself.

Rules:

- Start every agent shell command with `source ~/.devenv.sh && `.
- Do **not** install fnm, Homebrew git or a global pnpm (`npm i -g`), and do not edit `~/.zshrc` or other rc files.
  Conventions §1 still describes fnm and `/usr/local/bin/git`; PLAN.md wins on conflict (flagged for Marina).
- Check once per session: `source ~/.devenv.sh && node -v && pnpm -v && git --version &&
docker compose version` prints `v26.x`, `10.34.9`, git 2.31 or later and Compose 2.24.4 or later. If not, stop and
  report; never repair the machine.
- `.npmrc` `engine-strict=true` (phase 1a) turns a shell without the script into an install error.
- Playwright browsers are not part of Phase 0; 1a installs them (they need the lockfile's Playwright version).
- The docs changes of the consistency-pass re-review (ADR-0018, ADR-0019) are uncommitted on `main`'s working tree;
  they become the first commit of `feat/scaffold-tooling` (never a commit on `main`, conventions §2).
